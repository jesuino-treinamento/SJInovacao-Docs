    SJInovacao — Documento Consolidado (v4.0)¶

    Data: 19/10/2026
    Autor: Marcelo Jesuíno
    Status: Blocos D e E concluídos · 104 testes verdes · IoC Refatorado · Isolamento de Testes 100% · Auditoria de 2 Fases

    1. Visão Geral e Métricas¶

    O SJInovacao evoluiu para uma arquitetura de Modular Monolith madura, com isolamento completo entre os módulos (Registry e UserAccess). O sistema agora possui tratamento global de exceções, infraestrutura resiliente de banco de dados (Startup Migrations com Fail-Fast) e uma suíte de testes de integração que roda em ambiente isolado (Docker/Testcontainers), sem tocar no banco de desenvolvimento.

    Métricas Atuais¶

    Métrica v3.0 v4.0 (Atual)
    Módulos Funcionais 2 2 (Registry + UserAccess)
    Endpoints Ativos 47 47 (Bloco D finalizado)
    Testes Verdes 104 104 (71 Unit + 33 Integration)
    Isolamento de Testes Parcial (sujava o banco local) Total (banco sjinovacao_tests efêmero)
    Auditoria 2 Fases (incompleta) 2 Fases (Centralizada no Common)
    Infraestrutura (IoC) Híbrida (Legado + Novo) 100% Refatorada (SJInovacao.IoC)

    2. Conclusão do Bloco D — Endpoints do UserAccess¶

    Foram finalizados e estabilizados os 24 novos endpoints para gestão de acessos e permissões.

    Principais Correções e Refatorações:¶

    • Tratamento de Erros REST: O ExceptionHandlerMiddleware foi unificado. DomainException agora mapeia corretamente para 401 (credenciais), 404 (não encontrado) e 409 (conflito/duplicidade) em vez de estourar 500.
    • Padronização de Controllers: Remoção de blocos try/catch desnecessários nos controllers. O BaseController envelopa as respostas automaticamente via ApiResponse.

    3. Auditoria Unificada e Centralizada¶

    O serviço de auditoria foi movido definitivamente para o projeto SJInovacao.Common/Auditing, removendo dependências circulares entre os módulos Registry e UserAccess.

    Principais Correções:¶

    1. Padrão de 2 Fases (BuildPendingChanges + Materialize):
    2. Fase 1: Captura o snapshot antes do SaveChanges.
    3. Fase 2: O EF Core/PostgreSQL gera os IDs.
    4. Fase 3: O Materialize lê os IDs (inclusive chaves compostas) e grava os AuditLogs.
    5. Resultado: Fim definitivo dos EntityId zerados (Guid.Empty).
    6. Proteção contra Estouro de Campo (22001):
    7. A coluna EntityId foi alargada via migration para varchar(200).
    8. O AuditUserService aplica Truncate em todas as propriedades de texto antes de salvar no banco.
    9. Captura Robusta de Identidade:
    10. O CaptureHttpContext busca claims de sub, nameid, Name e email, garantindo que o UserId (Guid) e UserName sejam gravados corretamente.

    4. Infraestrutura, IoC e Banco de Dados¶

    4.1 Refatoração do IoC (Dependency Injection)¶

    • O legado (SJInovacao.Acesso.*) foi completamente removido.
    • ApplicationModuleInitializer e InfrastructureModuleInitializer: Centralizam MediatR, FluentValidation, AutoMapper e todos os Repositórios (Registry e UserAccess). O Program.cs está limpo.

    4.2 Startup Blindado (UseStartupMigrationsAsync)¶

    • Auto-Migrate: O Program.cs aplica as migrations na ordem correta (Registry -> UserAccess) via código, com ValidateOnBuild ativo.
    • Fail-Fast Schema Validation: O ValidateSchemaConsistencyAsync compara o HasMaxLength do modelo EF com o information_schema do Postgres. Se houver divergência, a API não sobe.

    5. Bloco E — Testes e Qualidade (104 Verdes)¶

    A suíte de testes foi blindada e agora roda de forma 100% isolada.

    • 104 Testes Verdes (0 Falhas):
    • Unit Tests (71): Domínio e Handlers (incluindo Auth).
    • Integration Tests (33): Usam Testcontainers e WebApplicationFactory.
    • Isolamento Absoluto (Testcontainers):
    • O RegistryApiFactory sobrescreve ambos os DbContexts para apontar para um banco no Docker.
    • O nome do banco foi alterado para sjinovacao_tests dentro do container, impedindo qualquer conexão acidental com o banco local (sjinovacao_dev).
    • O método EnsureDatabaseCreated() usa EnsureDeleted() + Migrate() para garantir um schema limpo a cada execução.
    • O ResetDatabaseAsync trunca as tabelas de ambos os módulos entre os testes.

    6. Próximos Passos¶

    1. Bloco J — Módulo Produtos: Iniciar o terceiro módulo do ERP, clonando a estrutura de pastas e a arquitetura de testes já validada neste ciclo.
    2. Bloco I — Pipeline CI/CD: Criar o arquivo .github/workflows/ci.yml para que o GitHub Actions faça o build e rode os 104 testes automaticamente em cada Pull Request. (Postergado devido ao repositório privado).
