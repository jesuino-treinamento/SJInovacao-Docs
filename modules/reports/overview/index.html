    📊 Módulo US08 — Relatórios Gerenciais (Reports)¶

    Módulo Baseado em CQRS (Read-Only)

    Este documento detalha o módulo de BI do ERP, focado em consultas paginadas e de alta performance sobre Materialized Views consolidadas a partir de múltiplos contextos transacionais.

    1. Visão Geral e Arquitetura¶

    O módulo Reports é um Bounded Context exclusivo para leitura (CQRS). Ele não possui comandos (Commands), apenas consultas (Queries). O acesso aos dados é feito por meio de Materialized Views que consolidam informações dos módulos de Vendas, Financeiro e RH, garantindo isolamento físico e performance sem onerar as tabelas de escrita transacional.

    • DbContext: ReportsDbContext (tabela de histórico __EFMigrationsHistory_Reports).
    • Repositório: IReportsRepository (implementado de forma híbrida com EF Core + Dapper).
    • Padrão de Resposta: PaginatedList<DTO> envelopado globalmente pelo ApiResponseWrapperAttribute.

    O fluxo arquitetural desenhado para o consumo e a atualização assíncrona concorrente dessas visões estrutura-se da seguinte forma:

    2. Modelo de Dados (Materialized Views)¶

    As views são criadas na migration Initial_Reports e atualizadas periodicamente de forma concorrente em segundo plano pelo worker MaterializedViewRefresher (com intervalo configurável via BackgroundJobs:MaterializedViewRefreshMinutes, padronizado em 5 minutos).

    erDiagram
    VW_SALES_DASHBOARD {
        Guid OrderId PK
        long OrderNumber
        string CustomerName
        DateTime OrderDate
        decimal TotalAmount
        string Status
    }
    VW_FINANCE_CASHFLOW {
        Guid TitleId PK
        string Type "Receivable | Payable"
        string Description
        decimal Amount
        DateTime DueDate
        string Status
    }
    VW_HR_WORKFORCE {
        Guid EmployeeId PK
        string FullName
        string DepartmentName
        string Status
        decimal BaseSalary
        DateTime HireDate
    }
    • vw_sales_dashboard: Filtra pedidos pagos, consolidando o nome completo do cliente resolvido via junção com a tabela compartilhada de pessoas (Persons).
    • vw_finance_cashflow: Operação de UNION ALL entre as tabelas de contas a receber (AccountsReceivable) e contas a pagar (AccountsPayable).
    • vw_hr_workforce: Consolida colaboradores ativos associando os dados estruturais de seus respectivos departamentos.

    3. Desafios de Engenharia de Dados Resolvidos (ADR-027)¶

    Durante o refinamento da malha de relatórios e a execução da suíte de testes de integração, três problemas impeditivos foram identificados e corrigidos:

    1. Incompatibilidade Crítica de Tipagem (Erro 500): A View Materializada realizava a projeção de chaves substitutas textuais de tabelas de escrita (o."Id" do tipo UUID/Guid) mapeando-as para campos de exibição como OrderNumber. Isso causava quebras e rollbacks silenciosos no Entity Framework Core no momento da serialização, pois os records C# da aplicação (SalesDashboardDto) esperavam tipos numéricos inteiros (long). A solução foi alterar a projeção da view para capturar o campo real de negócio (o."Number" AS "OrderNumber").
    2. Sensibilidade a Caixa Alta/Baixa (Case-Sensitivity): Diferentes submódulos de escrita geravam suas tabelas físicas de maneiras distintas no banco de dados. O módulo financeiro usava convenções PascalCase (ex: "Orders", "TotalAmount"), enquanto o módulo de RH utilizava tabelas geradas em lowercase puro (ex: employees, departments), resultando em falhas constantes de "coluna/tabela não encontrada" no PostgreSQL durante consultas manuais ou scripts fixos. A solução foi aplicar aspas duplas de escape explícitas apenas nas tabelas que usavam o padrão misto.
    3. Falha de Parametrização no Worker: O loop do MaterializedViewRefresher operava utilizando o método ExecuteSqlInterpolatedAsync para atualizar as views concorrentemente. O Entity Framework interpretava o nome da view passada de forma interpolada como um parâmetro de comando textual (convertendo-o para $1 no Postgres). O PostgreSQL nativo rejeita parâmetros posicionais de texto para identificadores de objetos estruturais. A solução foi adotar o método ExecuteSqlRawAsync injetando a string bruta sanitizada sob escape de aspas (\"{target.ViewName}\").

    4. Estratégia de Testes e Isolamento (Testcontainers)¶

    No ecossistema de testes de integração, descobriu-se um isolamento inadequado de conexões. O ReportsDbContext operava de forma desconectada da malha de contêineres temporários por não estar devidamente registrado no interceptor de ciclo de vida da Factory, gerando erros crônicos de 404 Not Found conforme esquematizado abaixo:

    Correção Aplicada na RegistryApiFactory:¶

    O ReportsDbContext foi incluído explicitamente na rotina de desconfiguração e reinjeção de escopos da factory de testes, forçando o contexto de relatórios a ler do mesmo container ativo: 

    services.AddDbContext<ReportsDbContext>(opt =>
    opt.UseNpgsql(_connectionString, b => {
        b.MigrationsAssembly("SJInovacao.Modules.Reports.Infrastructure.ORM");
        b.MigrationsHistoryTable("__EFMigrationsHistory_Reports");
    }));

    5. Endpoints Principais¶

    Todos os endpoints exigem autenticação ativa ([Authorize]) e suportam paginação nativa, ordenação dinâmica e busca textual flexível (search).

    Verbo Endpoint Descrição Latência Média
    GET /api/reports/sales Dashboard analítico de vendas e faturamento consolidado. 11ms - 25ms
    GET /api/reports/finance Visão consolidada de fluxo de caixa (Payables + Receivables). 15ms - 32ms
    GET /api/reports/hr Força de trabalho ativa agrupada por departamentos. 12ms - 19ms

    Parâmetros de query aceitos:

    • page (int, padrão 1): Índice da página desejada.
    • size (int, padrão 10, máximo 100): Quantidade de registros por página.
    • order (string, ex: "orderdate desc", "amount asc"): Ordenação de colunas da view.
    • search (string): Termo de busca textual filtrando por correspondência insensível (ILIKE) contra os campos principais de texto da respectiva view.

    6. Regras de Negócio do Módulo¶

    • Somente Leitura: É terminantemente vedada qualquer chamada que execute comandos de alteração de estado (INSERT, UPDATE, DELETE) nas tabelas através deste contexto.
    • Atualização Eventual Controlada: Os dados consultados pela API refletem o estado capturado no último ciclo de execução do REFRESH MATERIALIZED VIEW.
    • Paginação Mandatória: Nenhuma consulta à base analítica expõe coleções abertas; o uso de estruturas de segmentação de memória e contagem de registros (count(*)::int) é obrigatório.
