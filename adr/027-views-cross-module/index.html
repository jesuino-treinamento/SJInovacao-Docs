    ADR-027 — Estratégia de Sincronização e Nomenclatura para Visões Materializadas Cross-Module¶

    • Status: Aceito
    • Data: 2026-11-04
    • Decisores: Jesuíno, Inteligência Artificial
    • Contexto técnico: .NET 9, EF Core 9, PostgreSQL 16+, Npgsql, WebApplicationFactory, Testcontainers

    Contexto¶

    O módulo de Relatórios (Reports) consolida dados transacionais de múltiplos contextos isolados do ecossistema do ERP (como Vendas, Financeiro e Recursos Humanos) através de Materialized Views no PostgreSQL para garantir consultas analíticas de baixíssima latência (na casa de 11ms a 51ms).

    Durante o desenvolvimento e a execução da suíte de testes de integração, deparamo-nos com três problemas impeditivos na camada de dados:

    • Incompatibilidade Crítica de Tipagem (Erro 500): A View Materializada realizava a projeção de chaves substitutas textuais de tabelas de escrita (o."Id" do tipo UUID/Guid) mapeando-as para campos de exibição como OrderNumber. Isso causava quebras e rollbacks silenciosos no Entity Framework Core no momento da serialização, pois os records C# da aplicação (SalesDashboardDto) esperavam tipos numéricos inteiros (long).
    • Sensibilidade a Caixa Alta/Baixa (Case-Sensitivity): Diferentes submódulos de escrita geravam suas tabelas físicas de maneiras distintas no banco de dados. O módulo financeiro usava convenções PascalCase (ex: "Orders", "TotalAmount"), enquanto o módulo de RH utilizava tabelas geradas em lowercase puro (ex: employees, departments), resultando em falhas constantes de "coluna/tabela não encontrada" no PostgreSQL durante consultas manuais ou scripts fixos.
    • Falha de Parametrização no Worker: O loop do MaterializedViewRefresher (Background Service) operava utilizando o método ExecuteSqlInterpolatedAsync para atualizar as views concorrentemente. O Entity Framework interpretava o nome da view passada de forma interpolada como um parâmetro de comando textual (convertendo-o para $1 no Postgres). O PostgreSQL nativo rejeita parâmetros posicionais de texto para identificadores de objetos estruturais, quebrando a atualização automatizada em segundo plano.

    Adicionalmente, no ecossistema de testes de integração, o ReportsDbContext operava isolado sem que a RegistryApiFactory limpasse e reconfigurasse seu ciclo de vida para apontar para o contêiner dinâmico do Testcontainers, gerando erros crônicos de 404 Not Found no tráfego de leitura HTTP por consultar o banco de desenvolvimento local ou instâncias vazias.

    Decisão¶

    Decidimos adotar e padronizar os seguintes comportamentos de infraestrutura para o ecossistema de visões analíticas da aplicação:

    1. Alinhamento Estrito de Tipos com o Domínio: Toda e qualquer coluna projetada por uma visão materializada deve respeitar perfeitamente o tipo primitivo esperado pelo DTO/Record de leitura do C#. Identificadores numéricos sequenciais expostos a usuários finais devem mapear colunas transacionais correspondentes (como o."Number" AS "OrderNumber", que retorna long) e nunca identificadores de infraestrutura (como Guid).
    2. Ajuste de Caixa com Escrita Explícita: Scripts e migrations manuais do módulo de relatórios devem se adaptar de forma cirúrgica à escrita física existente de cada tabela gerada pelos módulos de escrita, fazendo uso de aspas duplas de escape sempre que houver variação no padrão de nomenclatura do Postgres (ex: misturar FROM employees e com LEFT JOIN "Customers" c).
    3. Refresher por SQL Puro (Raw SQL): Alteramos a execução do Background Service MaterializedViewRefresher para utilizar obrigatoriamente o método ExecuteSqlRawAsync. O nome da view é injetado diretamente na string do comando encapsulado por aspas duplas escapadas (\"{target.ViewName}\"), o que força o Postgres a interpretar o identificador estrutural nativamente sem criar parâmetros de texto textuais.
    4. Mapeamento Centralizado na Factory de Testes: Incluímos o ReportsDbContext de forma explícita no ciclo de vida de descarte de descritores e reinjeção da RegistryApiFactory. Com isso, todas as transações analíticas de teste compartilham rigorosamente o mesmo banco volátil do contêiner ativo, com rotinas de TRUNCATE automatizadas no encerramento de cada teste.

    Consequências¶

    Positivas¶

    • Desempenho Otimizado: Consultas analíticas rápidas (entre 11ms e 51ms) indexadas fisicamente no banco.
    • Estabilização Total: Eliminação completa dos Erros 500 de conversão e dos Erros 404 de isolamento de contexto no ambiente de testes de integração.
    • Segurança Sintática: Garantia de que modificações concorrentes nas tabelas físicas não travem o Worker de atualização contínua em produção.

    Negativas¶

    • Acoplamento Técnico Visual: O desenvolvedor precisa inspecionar e replicar a escrita exata de tabelas de outros contextos na migration analítica, aumentando a dependência manual na escrita de queries brutas.

    Neutras¶

    • Necessidade de Task.Delay em Testes de CQRS: Testes de integração automatizados que executam um POST e imediatamente realizam um GET no repositório precisam aguardar pequenos períodos de tempo (ex: 100ms a 200ms) para compensar o atraso do pipeline assíncrono de commit do MediatR/UnitOfWork no Testcontainer.

    Alternativas consideradas¶

    Alternativa 1 — Atualização Dinâmica via Entity Framework (LINQ)¶

    • Descrição: Mapear as views materializadas como DbSets comuns do EF Core e realizar consultas analíticas e atualizações parciais de dados utilizando expressões LINQ, deixando o ORM gerenciar os tipos.
    • Por que foi rejeitada: O Entity Framework Core não oferece suporte nativo para os comandos de reconstrução física de estruturas específicas do PostgreSQL (como REFRESH MATERIALIZED VIEW CONCURRENTLY). O uso de LINQ para consultas agregadas complexas de múltiplos módulos gerava joins pesados e ineficientes em runtime, anulando os ganhos de performance do banco.

    Alternativa 2 — Uso de ExecuteSqlInterpolatedAsync no Refresher¶

    • Descrição: Manter o uso do método de interpolação string do EF Core para manter a legibilidade sem precisar concatenar strings brutas no loop.
    • Por que foi rejeitada: Conforme diagnosticado nos erros de runtime, o método gera parâmetros SQL normais ($1), os quais não são aceitos pelo PostgreSQL para nomes de objetos de schema, impossibilitando a execução do comando do Background Service.
