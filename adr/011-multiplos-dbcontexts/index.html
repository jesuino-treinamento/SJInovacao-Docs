    ADR-011 — Múltiplos DbContexts em um Banco (Migrações e Tabelas Compartilhadas)¶

    • Status: Aceito
    • Data: 2026-10-15
    • Decisores: Marcelo Jesuíno
    • Contexto técnico: EF Core 9 · PostgreSQL 16 · Modular Monolith

    Contexto¶

    No padrão Modular Monolith, a recomendação é que cada módulo seja isolado. No entanto, compartilhar um único banco de dados físico (PostgreSQL) entre múltiplos módulos traz desafios. Originalmente, isso foi desenhado para os módulos Registry e UserAccess, mas o padrão foi validado e expandido para os 9 Bounded Contexts atuais.

    Os principais desafios superados foram:

    1. Conflito de Migrations: Se houver apenas um DbContext, o arquivo de migrations cresce descontroladamente e mistura regras de negócios de módulos diferentes.
    2. Acoplamento de Tabelas: O módulo UserAccess precisa ler/escrever na tabela Persons (que pertence ao módulo Registry). Se ambos tentarem criar a tabela Persons, o banco quebra (erro 42P07 - relation already exists).
    3. Integridade: Como garantir que as tabelas compartilhadas não sejam alteradas por engano pelo módulo que não é o dono?

    Mapeamento Arquitetural (Visão de Banco e Contextos)¶

    O diagrama abaixo ilustra como a aplicação gerencia as fronteiras lógicas, as permissões de escrita/leitura cruzada e os históricos isolados de migração dentro da mesma base física:

    Decisão¶

    Adotamos a estratégia de Múltiplos DbContexts no mesmo banco de dados, com ownership (propriedade) bem definido e tabelas de histórico de migrations separadas para cada módulo.

    1. Isolamento de Contextos e Ownership¶

    • RegistryDbContext: Dono absoluto das tabelas Persons, Addresses, Phones e AuditLogs.
    • DefaultContext (UserAccess): Dono das tabelas Users, Permissions, etc.
    • Os demais módulos (Products, Sales, Customers, Finance, Procurement, Employees, Reports): Cada um possui seu próprio DbContext (ex: ProductDbContext, SalesDbContext) e é dono absoluto de suas tabelas no banco.

    2. Exclusão de Migrations Cruzadas (ExcludeFromMigrations)¶

    Nos módulos que consomem o Shared Kernel (ex: UserAccess, Sales, Employees), mapeamos as entidades compartilhadas (Person, Address, Phone) e a tabela de AuditLogs, mas instruímos o EF Core a ignorá-las ao gerar as migrations:

    modelBuilder.Entity<Person>()
    .ToTable("Persons", t => t.ExcludeFromMigrations());

    3. Histórico de Migrations Independente¶

    Cada módulo possui sua própria tabela de histórico (__EFMigrationsHistory_*), garantindo que as migrations de um módulo não interferiram na contagem do outro. Atualmente, temos 9 tabelas de histórico no banco.

    4. Orquestração de Startup e Fail-Fast¶

    • A extensão UseStartupMigrationsAsync (DatabaseMigrationExtensions.cs) aplica as migrations na ordem correta de dependência (Registry → UserAccess → Products → Sales → Customers → Finance → Procurement → Employees → Reports).
    • Para evitar falhas silenciosas, foi implementado o ValidateSchemaConsistencyAsync, que compara o modelo EF (HasMaxLength) com o information_schema do PostgreSQL. Se o banco e o código divergirem, a API gera um erro estruturado e não sobe.

    Consequências¶

    Positivas¶

    • Fronteiras Claras: Cada módulo evolui suas próprias tabelas sem interferir no outro.
    • Migrations Menores e Rápidas: O isolamento simplifica os scripts e acelera a execução do pipeline de CI/CD.
    • Resiliência (Auto-Reset): O UseStartupMigrationsAsync gerencia o estado e detecta inconsistências em ambientes voláteis (como Docker de Dev ou Testcontainers) automaticamente.
    • Fail-Fast: A validação de schema impede que a aplicação suba com erros de tipagem latentes (ex: varchar(50) no banco vs varchar(200) no código).

    Negativas¶

    • Complexidade no Startup: Exige código de infraestrutura e orquestração customizado para encadear a inicialização dos contextos.
    • Transações Cruzadas: Realizar operações transacionais ACID complexas englobando múltiplos contextos (ex: criar Person e User na mesma transação atômica de infraestrutura) requer gerenciamento explícito na camada de aplicação, preferindo-se o uso de Eventual Consistency via mensagens.

    Neutras¶

    • Todas as connection strings apontam para o mesmo banco de dados físico único.
    • As migrations precisam ser geradas informando explicitamente os contextos desejados (-Context XxxDbContext).

    Alternativas consideradas¶

    Alternativa 1 — Um único DbContext (Monólito Tradicional)¶

    • Por que foi rejeitada: As migrations gerariam conflitos constantes caso múltiplas frentes de desenvolvimento atuassem em módulos distintos concorrentemente. Além disso, impossibilitaria ou dificultaria severamente uma futura extração de um submódulo de negócio para um microsserviço independente.

    Alternativa 2 — Dois ou mais bancos de dados separados (Database per Service)¶

    • Por que foi rejeitada: Complexidade prematura para a atual fase do projeto. Exigiria o uso imediato de coreografias complexas de transações distribuídas (Sagas) para manter a integridade imediata de fluxos simples entre todos os 9 módulos, além de elevar o custo operacional de infraestrutura para manter múltiplas instâncias isoladas.
